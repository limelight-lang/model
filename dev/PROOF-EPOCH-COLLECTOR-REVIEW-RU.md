# Заключение об оптимальности коллектора proof-epoch — второй раунд

Дата: 2026-10-03. Повторно проверена версия
`826b1bdcb7c639904f0255b907b9129d7e2edfbf` репозитория `model`.
Первый раунд относился к `b11f877`; перед публикацией получены три новых
коммита, и по запросу пользователя каждый из трёх критиков повторил разбор.
Предмет — [описание алгоритма](design/the-proof-epoch-collector.md), текущие
исходники, тесты и сохранённые данные S67.6. Рядом подготовлен
[русский перевод](design/the-proof-epoch-collector.ru.md).

В обоих раундах проведены три независимых разбора: алгоритмическая стоимость и прогресс;
задержки мутатора и время жизни памяти; методика и результаты измерений.
Их замечания ниже сведены и проверены по исходникам. «По коду» означает
статический вывод; «пересчитано» — анализ сохранённых данных, а не новый
нагрузочный запуск. Предложения по изменению алгоритма не реализованы.
Номера строк относятся к `826b1bd`, если другая версия не названа явно.

## 1. Заключение

**Коллектор proof-epoch, измерявшийся как bestD, обоснован для проверенных
веб-нагрузок и принят владельцем проекта как default. Его общая
оптимальность, ограниченная задержка освобождения и отсутствие регрессии
задержек не установлены.** Наиболее сильный результат — уменьшение объёма
мусора на `web-heap` и отсутствие остатка во всех пятнадцати запусках
после 12-секундной завершающей сборки. Ускорение CPU из данных не следует.

В архитектуре стоит сохранить общие теневые строки на пакет, поиск
коллектором и точную проверку владельцем ограниченного предложением
множества. Это сокращает повторное раскрытие общего графа и обход живого
окружения на мутаторе. Однако размер этого множества не ограничен числом
корней, а проверка владельца, деструкторы и физическое освобождение остаются
его работой.

Три главных препятствия более сильному заключению:

1. В `mark` есть конструкция с квадратичным числом чтений удержанных записей.
2. Постоянное прерывание до завершения большой циклической компоненты
   не получает общей гарантии прогресса; Q1 оставлен открытым самим планом.
3. После обнаружения `stop` остаётся работа, зависящая от размера обхода.
   Порог отзыва не ограничивает ни длительность удержания токена, ни объём
   отложенных возвратов, ни последующую паузу владельца.

Новый английский документ фиксирует принятие default 2026-10-03
(`dev/design/the-proof-epoch-collector.md:3–8`). Поэтому прежнее утверждение
нашего отчёта «выбор ещё не принят» снято. При этом `default = []`
в `Cargo.toml:19` всё ещё не включает `wait-by-readings`, а
`PLAN.md:581–591` ещё ожидает ответа. Решение принято; настройки сборки
и план не синхронизированы с ним. Для описанного поведения на этом коммите
нужен явный `--features wait-by-readings`. Анализ не меняет принятое решение.

## 3. Замечания критиков

### R1. Высокий приоритет: повторные held-проходы имеют квадратичный худший случай

**По коду.** `src/cycle/mark.rs:383–424` повторно читает все ещё ненулевые
удержанные строки и перекладывает их в следующий стек.
`src/cycle/arena.rs:1268–1288` меняет стеки местами. При вычитании последнего
ребра из уже встреченного ребёнка готовая запись немедленно в работу
не ставится (`src/cycle/mark.rs:802–810`).

**Контрпример.** Один корень пакета `r` с внешним владельцем имеет прямые
рёбра во все зарегистрированные `v1…vN`, не входящие в пакет и не несущие
актуальных меток отсечения. Дополнительно
есть `vi → v(i+1)` и `vN → r`. После раскрытия `r` строка `v1` равна нулю,
у остальных остаётся единица. Порядок прямых рёбер можно выбрать так,
чтобы первый стек выдавал при N=6 записи `[2,4,6,5,3,1]`. Проходы читают:

```text
[2,4,6,5,3,1]  — раскрывается v1
[3,5,6,4,2]    — v2
[4,6,5,3]      — v3
[5,6,4]        — v4
[6,5]          — v5
[6]            — v6
```

Каждая вершина раскрывается один раз, но удержанные записи читаются
`N(N+1)/2` раз при линейном числе вершин и рёбер. Поэтому утверждение
оригинала об однократном раскрытии не означает линейную стоимость `mark`.
Существующий тест простой зарегистрированной цепочки встречает очередного
ребёнка впервые уже внутри прохода; он не покрывает заранее удержанную цепь
(`src/cycle/mark/tests/the_held_stack.rs:222–262`).

Минимальная модель двух стеков, нулевых строк и этих вычитаний выполнена
отдельно от runtime. Она дала 2 080 / 8 256 / 32 896 / 131 328 / 524 800
чтений для N=64/128/256/512/1024. Это подтверждает расчёт модели;
новый Rust-тест на реальной куче в этой работе не добавлялся.

**Варианты.** Очередь готовых удержанных записей при переходе строки в ноль:
дополнительное состояние `held/queued/expanded` и проверка при вычитании,
в основном на стороне трассировки. Более простой предел числа проходов
с переходом в окончательный обход сохраняет итог полного `mark`, но
ухудшает порядок полезной работы до прерывания.

**Приёмка.** Реальный граф выше, N с удвоением; счётчик всех извлечений
из held, равенство итоговых строк обычному обходу, остановка внутри очереди.
Линейность проверять по операциям, а не по числу раскрытых объектов.

### R2. Высокий приоритет: общая гарантия прогресса шире реализации и тестов

В §9 оригинала обещано освобождение мусора за ограниченное число эпох.
Но `dev/plans/S67.md:3780` прямо оставляет открытым Q1: мусорная компонента,
чей обход не укладывается в одно окно владения токеном.

**Контрпример по коду.** При положительном cap есть большой мусорный цикл
без актуальных меток; в R представлен только один
его участник; остальные участники не становятся корнями следующих пакетов.
Каждый обход останавливается до замыкающего ребра.
У корня остаётся положительная строка. При пакете из одного корня публикуется `ReadLive`
(`src/cycle/worker.rs:2968–2989`), корень откладывается, затем начинается
такой же обход с начала. Продолжение не сохраняется, завершённого
доказательства и меток нет. Частичное множество не позволяет освободить
строгую часть цикла: входящее ребро из оставшейся части удерживает её
при точной проверке. Одни смены эпох не устраняют повторение.

Это граница фоновых обходов при данных отзывах. Отдельный успешно
завершившийся синхронный обход всего R, например на пути pressure/exit,
может освободить такой цикл; его работа и задержка должны входить
в условия гарантии, если прогресс обеспечивается именно им.

Во втором раунде отдельно проверены автоматические пути. При положительном
cap истечение interval и достижение threshold ведут к обычному пакету
коллектора (`src/cycle/worker.rs:1198–1202,1438–1448,1480–1504`).
Для малого R используется форма standing take, которая вообще не читает
и не подстраивает K (`src/cycle/worker.rs:2196–2207`). Возврат отложенной
очереди не ставит запрос whole-R (`src/gc.rs:310–319`). Обязательного
перехода к полной сборке владельца после N неудачных пакетов нет.
`ASKED` при cap=0 и pressure — отдельные причины `Arming::AllRoots`
(`src/cycle/worker.rs:1363–1373`, `src/gc.rs:81–100,389–423`).

Постоянные отзывы не требуют неизбежного memory pressure: несвязанные
сущности можно освобождать и заново выделять из возвращаемого после grant
запаса. Это конструкция для будущего теста, не выполненный runtime-сценарий.

Тест `src/cycle/worker/tests/the_progress.rs:198–218` выставляет отзыв
между `mark` и `scan`, уже после `mark`; это другой случай. Успешная
завершающая сборка после остановки нагрузки также не доказывает продвижение
при непрерывных освобождениях и повторных отзывах.

**Требуемая граница утверждения.** Нужны конечный обслуживаемый граф,
достаточная память, работающие безопасные точки владельца и возможность
завершить достаточный обход. Общий предел числа эпох без этих условий
из текущей реализации не следует; предел времени тем более не следует.

**Варианты и цена.** Сохраняемое продолжение требует протокола времени жизни
и проверки изменившихся рёбер. Гарантированное непрерывное окно либо
синхронный обход оплачиваются задержкой и удержанием памяти.
Просто уменьшить бюджет обхода или порог отзыва недостаточно.

**Приёмка.** Большая SCC, детерминированный stop до обратного ребра
на протяжении 32 и более обходов/эпох. Затем проверить явно выбранное
условие, при котором реализация обязана завершить освобождение.
Отдельно измерить возраст мусора при продолжающейся нагрузке.

### R3. Высокий приоритет: после stop остаётся большой хвост удержания токена

**По коду.** Работа после остановки зависит от фазы и наличия предложений.
В ветке снимка при наличии `Proposed` остаются сброс окраски
`src/cycle/scan.rs:244–256`, построение нулевого замыкания и множества
`src/cycle/posted_set.rs:198–240`
(`src/cycle/worker.rs:2997–3008`). Без предложений эти действия пропускаются,
но `arena.reset()` остаётся; затем идут сортировка и публикация множества,
если оно есть (`src/cycle/worker.rs:2402–2407`). Сброс снимает связи
с памятью владельца и возвращает метаданные, в том числе вызывает
отбрасывание физических страниц (`src/cycle/arena.rs:996–1071`).
В другой ветке — записи меток после завершённой трассировки — разворот
и восстановление списка массивов также идут без проверки отзыва
(`src/cycle/collector_stamps.rs:171–179`). Это не последовательные стадии
каждого stop: во втором раунде прежнее обобщение уточнено.

При отзыве текущего токена `read_the_recall_now` возвращает `Break`
раньше вызова `release_the_grants_behind`
(`src/cycle/arena.rs:1613–1618`). Поэтому другой мутатор, уже согласившийся
на ещё не начатый обход, может ждать и этот хвост. Величина
`RECALL_STRIDE=1024` ограничивает интервал обнаружения сигнала на
проверяемых участках, а не всю работу до отдачи токена.

**Измерено ранее:** S65.17 сообщает до 185 мс и 582 удержанных блока
при пороге 16. Это запуск стандартного D на `c52ff90`; его исходные CSV
не сохранены в репозитории. Числа нельзя выдавать за отдельно пересчитанный
замер bestD или за измерение вклада каждой перечисленной функции.

**Варианты и цена.** Отделить обязательное снятие всех связей с памятью
владельца от возврата собственных метаданных коллектора; исследовать
выпуск токена до второй части. Отзыв разрешений ещё не начатых обходов
обслуживать независимо от прекращения текущего обхода. Ранний выпуск
до снятия связей небезопасен. Новый жёсткий предел блоков без решения R2
может снова лишить большую компоненту прогресса.

**Приёмка.** Два мутатора, один коллектор, одновременно отозванные токены
A и B; граф A с растущим числом затронутых блоков, обход B ещё не начат.
Отдельно снять время построения снимка и множества, снятия связей с памятью
владельца при reset, возврата метаданных и отбрасывания страниц,
сортировки/публикации множества, выпуска токена и физического возврата
удержанной памяти. `set.append` идёт до reset, а сортировка в `set.publish`
после него. Также снять пик удержанных байтов и работу мутатора.
Отсчёт начинать с выставления recall, отдельно измеряя его обнаружение;
после release учитывать ожидание следующего free/poll владельца.
Вытесненный коллектор и спящий владелец не дают предела реального времени
даже при ограниченном числе операций. Сценарии с `Proposed` и без него
проверять раздельно.
Нулевого `token_wait_longest_us` в S67.6 для этой проверки недостаточно.

### R4. Высокий/средний приоритет: K не ограничивает работу владельца

**Первое, высокий приоритет для задержек:** множество `posted_set`
намеренно не имеет ограничения, кроме доступной памяти
(`src/cycle/posted_set.rs:43–53`). Один корень способен предложить большую
компоненту. Владелец учитывает, трассирует и сканирует всех участников
(`src/cycle/trace.rs:161–195`), выполняет точное подтверждение, деструкторы,
повторное подтверждение и освобождение
(`src/cycle/collect.rs:1428–1479`). Поэтому даже K=1 допускает длинную
паузу в одной безопасной точке.

Разделение независимых компонент на предложения может распределить эту
работу между опросами. Произвольное разрезание одной SCC не обеспечивает
прогресса: каждый кусок может выглядеть внешне удерживаемым. Проверять
нужно семейство больших колец, в том числе с воскрешающими деструкторами,
и полную длительность обработки P, а не только ожидание токена.

**Второе, средний приоритет:** после возврата токена один free/poll
сливает накопленные стеки возвратов без квоты. Если в процессе выдан новый
токен, `splice_behind_the_head` ищет хвост всего остатка
(`src/cycle/deferred_slot_reuse.rs:1126–1193,1258–1312`). Повторяющиеся
короткие разрешения способны добавлять линейные обходы без сопоставимого
освобождения. Хранение хвоста или отдельного остатка требует дополнительного
состояния; квота возвратов уменьшает паузу ценой удержания памяти.
Приёмка — новый grant после первого возврата длинной цепочки, учёт
посещённых звеньев, отсутствие потерь, полный возврат при pressure/exit.

**Третье, средний приоритет:** индекс блоков `posted_set` сортируется
отдельно в каждом блоке метаданных, а отрицательный поиск при возврате
постороннего блока проходит всю цепочку (`src/cycle/posted_set.rs:273–275,
367–398`). При B блоках графа, C адресах в блоке индекса и F посторонних
возвратах стоимость составляет `O(F × ceil(B/C) × log C)`. Положительное
совпадение отменяет и синхронно уничтожает всё множество.

Единый неизменяемый индекс может строить коллектор; это дополнительная
память и работа построения. Проверить отрицательные возвраты при индексе
из 1/2/4/8 блоков и обязательную отмену до переиспользования либо unmap.
Численный вклад обоих последних путей на текущих веб-нагрузках не установлен.

### R5. Средний/высокий приоритет: метки зависят от размещения, а правило эпохи — эвристика

**По коду.** Метки получают живые строки только тех массивов строк,
которые впервые затронуты после начала окончательного обхода
(`src/cycle/arena.rs:1321–1347`, `src/cycle/collector_stamps.rs:78–94`).
Это признак блока, а не доказанная классификация каждой сущности
как долгоживущего состояния. Сам модуль признаёт также обратную ошибку:
временный запрос, раскрытый в окончательном обходе, может получить метку
(`src/cycle/collector_stamps.rs:14–21`).

**Контрпример повторной работы.** Изначально нештампованный,
зарегистрированный долгоживущий vector/hash array из N скалярных значений
с целочисленными ключами, на который указывают временные корни. Его строка
появилась до окончательного обхода, при удержании. Массив не считается
листом (`src/cells.rs:612–639`), и окончательный обход читает его N позиций,
но новых дочерних строк нет. Метки на самом массиве не возникает; следующие
пакеты снова читают позиции. Аналогично раннее касание части блока исключает
из записи меток живые строки этого же блока, раскрытые позднее.

Это статические конструкции, пока без нового runtime-теста. Их следствие:
фраза §9 «завершённый пакет ставит метки на обойдённое состояние» должна
наследовать ограничение §4 на новые массивы строк.
Речь о последовательности обычных фоновых пакетов: отдельный обход
владельца по всему R может изменить историю меток данного объекта.

**Вариант и цена.** Учитывать фазу отдельных строк либо отдельно исследовать
метки живых удержанных границ. Цена — метаданные, операции трассировки
и риск дольше откладывать временные графы. Проверить неизменный большой
scalar vector/hash в нескольких пакетах одной эпохи и один граф
при раздельном/смешанном размещении request/core; считать позиции обхода,
а также задержку освобождения после смерти внешнего владельца.

Дополнительно `spent ≥ 2 × proving` — оценочное правило, не доказательство
окупаемости меток. Цена основана на
`final_drain_positions × stamps / final_drain_rows`
(`src/cycle/worker.rs:2814–2819`); в последующую работу входят все позиции,
а не реально сэкономленные обходы. Дорогой несвязанный мусор может быстро
сменить эпоху после дешёвого доказательства. Полезность отношения 2 нужно
оценивать по повторному обходу, памяти и CPU; соответствующее предложение
остаётся эвристикой.

### R6. Высокий приоритет для выбора конфигурации: окна CPU различаются, задержки не разрешены

Основная формула складывает CPU мутаторов за цикл от стартового барьера
(116 с, включая прогрев) с полным CPU коллектора к остановке, включающим
его работу при подготовке. Отдельная оценка CPU коллектора вычитает снимок
после прогрева (96 с рабочего окна), но делится на запросы за 116 с.
Источники: `dev/data/s67.6/analyse.py:15–17`,
`src/cycle/worker/tests/the_rig.rs:2112–2115,2158,3377–3387,4315–4330`.
В измеренном `a72693d` этот код такой же.

Числа верно воспроизводят опубликованную формулу, однако не выражают
чистую стоимость запроса за единое рабочее окно. Простая замена одного
столбца коллектора оставит несовпадающие окна. Нужны синхронные снимки
CPU мутаторов и коллектора на границах окна и запросы того же окна;
подготовку, прогрев и завершающую сборку следует учитывать отдельно.

Пересчитанная медиана пяти парных p99.9 разностей bestD минус D:

| Нагрузка | От поступления запроса, мс | От начала обслуживания, мс |
| --- | ---: | ---: |
| `web-arena-40k` | 16,623 | 7,632 |
| `web-arena-150k` | 17,851 | 6,648 |
| `web-heap` | 166,385 | 89,394 |

Это p99.9 разностей сопоставленных запросов, а не разность двух p99.9.
Идентификаторы и параметры пар совпали. Однако A/A проведён только
одной парой для 40k и heap; получены 31,7 и 120 мс, для 150k пары нет.
Регрессию нельзя ни надёжно подтвердить, ни исключить. CPU-допуски
9–17,5 % для bestD/D также не разрешают исходную цель 3 %.

**Приёмка.** Повторные перемежающиеся A/A и A/B на одинаковом размещении,
единые окна, оценка разброса эффекта и достаточное число хвостовых наблюдений.
Затем контрольные нагрузки, cap-4 и насыщенные ядра. Наблюдение
`token_wait_longest_us=0` означает отсутствие ожиданий take в этих данных,
а не проверенную малую задержку отзыва или физического возврата памяти.

### R8. Новый результат: пустой production poll исправлен; перенос результата ограничен

**Что изменено в коде.** `Cell<u8>` с преобразованием в enum заменён
на `Cell<Arming>`, `None` отделён одной проверкой, а исполнение запроса
вынесено в `#[cold] #[inline(never)] fire`
(`src/gc.rs:40–43,141–144,353–359,379–423`). Пять видов запроса и их
приоритеты сохранены. По статическому сравнению новых ошибок поведения
в этой перестройке не найдено.

**Что измерено по новому журналу.** S65.30 сообщает 183 → 175 исполняемых
инструкций на пустой poll зарегистрированного потока, −4,37 %, с возвратом
к 175 инструкциям базы этапа. Один переход к enum дал 182; вынос обработки
запроса довёл результат до 175. Использован Callgrind и release-библиотека
без `cfg(test)`, два миллиона вызовов
(`dev/BENCHMARKS.md:11–36`). Это полезное исправление частого пути.

**Чего результат не устанавливает.** Он не измеряет реальное время,
пропускную способность веб-нагрузки или p99.9 задержки. Даже poll без
запроса сборки может выполнить обслуживание: возврат отложенных очередей
и накопленной памяти происходит до новой проверки `Arming::None`
(`src/gc.rs:317–327,354–358`). Поэтому R3/R4 остаются в силе.
Стоимость непустых ветвей новая серия также не оценивает; утверждать
их ускорение или регрессию по ней нельзя.

**Ограничение воспроизводимости, средний приоритет.** В репозиторий
не добавлены исходник вспомогательного production probe, необработанный
Callgrind, полная команда сборки, версии инструментов и hash конечного
бинарника. Число 175 здесь приводится как опубликованный результат,
согласованный с механизмом кода, но независимо в этом разборе не измеренный.
Для воспроизведения нужны перечисленные артефакты и повторный счёт.

**Разные сборки.** S67.6 использовал тестовые release-бинарники
(`dev/data/s67.6/README.md:11–12`). Новый журнал отдельно показывает
накладные расходы test-only hooks: тестовый probe даёт 224 против 171
инструкции, которые нельзя смешивать с production-числом 175.
Это не отменяет сравнение четырёх вариантов внутри S67.6, но ограничивает
перенос абсолютного CPU на production. Накладные расходы могут зависеть
от частоты разных путей. Вычитать восемь инструкций из старых запросов
или умножать их CPU на отношение результатов этих probes нельзя.
Нужна нагрузка на production-библиотеке с сопоставимым учётом работы.

Отдельное изменение `src/cycle/token/testing.rs:73–105` убирает таймер
в одной ветви тестового держателя токена: sender закрывается при release
или Drop. Оно исправляет время жизни фикстуры для виртуальных часов Miri,
но не меняет production recall/consent и не ограничивает его задержку.
Miri в этом разборе не запускался.

## 4. Рекомендуемый порядок дальнейшей работы

1. Синхронизировать настройки сборки и план с принятым default; уточнить
   границы утверждений в описании и зафиксировать большой
   постоянно прерываемый цикл как отдельный критерий прогресса.
2. Добавить реальные воспроизводимые сценарии R1 и R5; измерить число
   операций, а не только итоговую длительность.
3. Разложить задержку из R3 на фазы и сначала убрать необязательную работу
   под токеном, сохраняя протокол времени жизни. Отдельно измерить всю
   паузу владельца из R4.
4. Исправить окна измерений; повторить D/bestD с A/A, исходными контрольными
   нагрузками и непрерывным учётом возраста мусора. Только после этого
   оценивать настройку K, X, отношения стоимости доказательств и ожиданий.
5. Для принятого default отдельно зафиксировать цену по CPU, пику памяти,
   возрасту мусора и задержкам. Текущие данные дают сильный довод за bestD
   по памяти на `web-heap`, но не снимают остальные критерии. Новый выбор
   default для выполнения этого анализа не требуется.
