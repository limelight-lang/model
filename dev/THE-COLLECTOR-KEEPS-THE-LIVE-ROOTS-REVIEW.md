# Коллектор хранит живые корни: критика и варианты исправления

Дата: 2026-09-26. Объект ревью —
[The collector keeps the live roots](design/the-collector-keeps-the-live-roots.md)
в коммите [`5020d2a`](https://github.com/limelight-lang/model/commit/5020d2a095e4435e09e27b0c75e8787917da6248).
Ссылки с номерами строк ниже закреплены за этим коммитом. Проверены код
этой ветки, её `PLAN.md`, история измерения и появления `live_list`.

Статус: критика предложения и возможные решения, не принятое изменение
алгоритма и не новый этап плана. Цепочка ещё не построена. Контрпримеры
ниже разобраны по правилам предложения; испытания для них описаны как
критерии будущей реализации, а не как выполненные прогоны. Новых измерений
производительности в этом ревью нет.

Под цепочкой C здесь понимается предлагаемое постоянное хранилище корней,
а не существующий `live_list` участников прочитанного живого подграфа.
R — очередь кандидатов, P — очередь вердиктов. Форма D — предложенный
проход мутатора по P без открытия трассировки, когда в P нет `Proposed`.

## Заключение

Правило выбора, уточнённое владельцем 2026-09-26: **мутатору меньше
операций, коллектору больше операций**. Поэтому обычные живые корни,
повторные попытки, проверка смертей и её расписание должны оставаться у
коллектора. Возврат через мутатора ради упрощения коллектора не является
предпочтительным исправлением.

Форма D имеет самостоятельное основание: при отсутствии `Proposed`
обработка вердиктов не требует поиска графа. В опыте она служит отдельным
контролем, чтобы выделить дополнительный выигрыш C. Целевой обычный путь
для полностью живого batch — без постов в P и без прохода мутатора.
Для самой C пока не замкнуты правила
выхода, продвижения между источниками, отзыва токена и обнаружения смертей.
У численного обоснования есть проверяемая ошибка происхождения данных.

| Работа | Предпочтительный исполнитель |
|---|---|
| Хранение `ReadLive` и `Unwalked`, порядок повторных попыток и смена эпохи | Коллектор |
| Курсор проверки смертей, её бюджет, срок следующей проверки и накопление результата | Коллектор |
| Выбор R/C, резервирование P, упаковка и передача подготовленных записей | Коллектор |
| Выбор формы D по наличию `Proposed` и публикация этого выбора в token byte | Коллектор; мутатору не нужен предварительный проход по P |
| Точное подтверждение `Proposed`, деструкторы и физическое освобождение | Мутатор, как требует модель |
| Полный просмотр C при pressure/exit и обработка отказа её хранения | Мутатор на этих исключительных путях |

Больше работы коллектора допустимо, пока она не возвращается мутатору
большим ожиданием токена, давлением памяти или конкуренцией за CPU. Это
проверяется по результату мутатора, а не по минимуму общей суммы инструкций.

| Замечание | Что установлено | Что необходимо решить |
|---|---|---|
| F1 | Выходу предписаны только истёкшие блоки C; это слабее существующего обхода всех отложенных корней | Читать всю C перед каждым раундом выхода |
| F2 | Приоритет C перед R допускает голодание R | Гарантировать продвижение каждого источника и порядок повторных попыток |
| F3 | Проверка всех заголовков C не ограничена K; её отзыв и продолжение не описаны | Ограничить порцию работы и сохранять место продолжения |
| F4 | Порог смертей проверяется внутри grant, но сам его не вызывает | Выбрать и описать механизм запуска либо честно оставить ожидание эпохи |
| F5 | Число 15 365 получено до появления stamping из live list | Исправить атрибуцию и измерить актуальную базу |
| F6 | Общий результат не отделит выгоду формы D от выгоды C | Сравнить текущий код, только D и D вместе с C |

## F1. Выход должен читать всю цепочку независимо от эпохи

**Основание.** В предложении,
[«The mutator's deferred lane goes», строки 95–104](https://github.com/limelight-lang/model/blob/5020d2a095e4435e09e27b0c75e8787917da6248/dev/design/the-collector-keeps-the-live-roots.md#L95-L104),
выход вместе с обычными собственными сборками читает только истёкшие
блоки C. В конце выхода цепочка разбирается.

Контрпример: корень цикла помещён в C как живой; последняя внешняя ссылка
исчезает; поток выходит до смены эпохи. Candidate bit уже установлен,
поэтому decrement не создаёт новой записи в R. Выход не исследует цикл.
Освобождение блоков C возвращает память записей, но не выполняет
пропущенную финализацию объектов.

В существующем
[`collect_before_exit`](https://github.com/limelight-lang/model/blob/5020d2a095e4435e09e27b0c75e8787917da6248/src/cycle/collect.rs#L658-L695)
вся deferred lane предлагается заново перед каждым раундом независимо от
эпохи. Повторение существенно: деструктор раунда может убрать последнюю
внешнюю ссылку на другой цикл, который этот раунд ещё прочитал живым.

**Предпочтительное исправление.** Выход, как и поиск под давлением памяти,
читает C целиком. Перед каждым раундом выхода вновь доступны все её
оставшиеся корни, в том числе отложенные предыдущим раундом. Токен остаётся
у мутатора до конца выхода. Остаток после существующего ограничения числа
раундов или отказа учитывается явно; в него не попадает объект только
потому, что stamp ещё свежий.

Предпочтительнее дать exit-batch прямой источник C без фильтра эпохи:
мутатор не копирует её записи в R перед тем, как их прочитать. C входит в
учёт продвижения и остатка выхода. Перенос C в R допустим как альтернативное
представление только при доказанном переносе блоков без копирования корней
и выделения памяти; дополнительный проход мутатора ради удобства адаптера
не соответствует выбранному правилу.

Цена полного просмотра при выходе уже входит в существующий контракт.
Для обычного `cap 0` полный просмотр свежей C из этого исправления не
следует: у выхода собственное основание — следующей эпохи потока не будет.

**Проверки будущей реализации.** Неистёкший припаркованный цикл без
внешней ссылки освобождается на выходе; деструктор первого раунда делает
такой цикл мусором, второй его находит; отдельно отказ и предел раундов
оставляют корректный учтённый остаток. Удерживаемый reading hold задерживает
возврат блоков C, но не подменяет обход объектов возвратом блоков записей.

## F2. Приоритет C не должен лишать R продвижения

**Основание.**
[Строки 28–30 и 44–49](https://github.com/limelight-lang/model/blob/5020d2a095e4435e09e27b0c75e8787917da6248/dev/design/the-collector-keeps-the-live-roots.md#L28-L49)
помещают `Unwalked` в уже истёкшую C и читают истёкшую C впереди R.
Общая вместимость batch ограничена.

Первый контрпример: K корней C снова остаются `Unwalked` из-за отзыва
при обходе их первой трудной компоненты. На следующем grant они вновь
впереди R. Лёгкая мусорная компонента в R может никогда не получить попытки.
В текущей схеме
[`dispose_verdicts`](https://github.com/limelight-lang/model/blob/5020d2a095e4435e09e27b0c75e8787917da6248/src/cycle/queue/compaction.rs#L270-L284)
возвращает эти корни в R через `append_entry`, за уже стоящими записями.

Второй контрпример не требует отзыва. Пусть собственная сборка мутатора
оставила в C 70 000 живых корней, K достиг 1 024, а R содержит новый мусор.
Вся C истекает; за 64 batch коллектор проверяет не более 65 536 корней.
По существующему правилу 64 batch меняют эпоху. Пока последние корни ещё
ждут первого просмотра, уже перепаркованные снова истекли. При строгом
приоритете C она может оставаться непустым истёкшим источником постоянно.
Это допустимое расписание описанного предложения, а не результат прогона.

**Предпочтительное исправление.** `Unwalked` остаётся у коллектора в
готовой части C и ставится за уже ожидающими повторными попытками.
`ReadLive`, включая консервативный вердикт после исчерпания бюджета,
остаётся в части C, ожидающей эпохи. Это логические состояния записей;
нужны ли две физические цепочки или очередь готовых блоков, должна решить
раскладка и её измерение. Коллектор сам переводит истёкшие блоки в готовые
и поддерживает порядок; обычный `Unwalked` не проходит через P и мутатора.

Для R и готовой C задать доли одной ограниченной порции. При двух
непустых источниках каждый получает положительную долю; если места
хватает только одному, следующий grant начинает со второго источника.
Неиспользованную долю может взять другой источник.

Квота на копирование сама по себе недостаточна. Если трассировка всегда
начинается с трудного корня C и заканчивается отзывом, скопированные
корни R всё равно остаются непрочитанными. Поэтому нужно также чередовать
первый источник обработки и возвращать незавершённые попытки за уже
ожидающими корнями. Эти перестановки и состояние чередования принадлежат
коллектору; отдельный сигнал из poll не нужен. Гарантия относится к
получению попытки при выдаваемых
grant, а не к завершению произвольной компоненты при бесконечных отзывах.

Цена — состояние очереди готовых попыток, владение записями и правила
удаления блоков на стороне коллектора. Называть её частью «бесплатных
16 байт» до раскладки нельзя. Нельзя также дважды учитывать один корень
как готовый и ожидающий эпохи.

**Путь отказа.** Возврат `Unwalked` через P в R сохранить там, где память
для владения у коллектора получить нельзя или требуется гарантированное
завершение unwind. Место в P резервируется заранее. Это страховка
сохранности записи, а не обычная плата мутатора за повторную попытку.

**Проверки будущей реализации.** Обе формы контрпримера; P почти заполнена;
один доступный слот; поступление новых корней во время обработки;
повторный отказ и recall. Считать отдельно попытки из R и C и возраст
самой старой ожидающей записи. Публикации смертей также не должны постоянно
отнимать все места у корней, которым ещё требуется трассировка.

## F3. Проверка смертей требует ограниченной порции и продолжения

**Основание.**
[«Completed deaths in the chain», строки 69–77](https://github.com/limelight-lang/model/blob/5020d2a095e4435e09e27b0c75e8787917da6248/dev/design/the-collector-keeps-the-live-roots.md#L69-L77),
предписывает на каждом grant читать заголовок каждого корня C. Число этих
чтений не ограничено K. Даже без трассировки это холодные обращения под
токеном; они продлевают удержание освобождений и ожидание возврата токена.
Предложение не задаёт для прохода проверку recall и способ продолжения.

Текущий
[`trace_in_parts`](https://github.com/limelight-lang/model/blob/5020d2a095e4435e09e27b0c75e8787917da6248/src/cycle/worker.rs#L2443-L2474)
проверяет отзыв даже перед каждым заголовком первоначального прохода.
Новому проходу нужна не более слабая дисциплина. Начинать после каждого
отзыва снова с головы недостаточно: хвост тогда может никогда не читаться.

**Предпочтительное исправление.** Разделить выбор корней для трассировки и
проверку завершённых смертей. У проверки — ограниченная порция H позиций
и сохраняемая позиция следующего просмотра. Проверка recall входит в тот
же протокол, который обслуживает отзыв собственного токена и грантов,
стоящих за этим batch. При отзыве заканчиваются новые чтения, сохраняются
уже выполненные перемещения и позиция, затем выполняется ограниченное
завершение и возвращается токен.

H — новый параметр опыта, не выбранная этим ревью константа. Постоянный
курсор находится у коллектора и добавляет память и обязанности: изменение C мутаторам разрешено
только под токеном; при удалении блока курсор должен быть переведён на
живое продолжение до возврата блока. Нужно показать место его хранения,
а также обновление и очистку при выходе. Одного указания на release-store
недостаточно для доказательства времени жизни адресуемого блока.

**Вместимость и владение.** До удаления записи из её источника за ней
резервируется место назначения. Для скопированных корней сохраняется
возможность непроваливающегося unwind в P. Пост смертей использует только
оставшуюся комнату; смерть, которой места не досталось, остаётся в C с
candidate bit. Найденные смерти коллектор накапливает в собственной
готовой части, не перечитывая их как живые корни. Её владелец, предел,
место под запись и путь отказа должны быть описаны так же, как у остальных
записей C. Candidate bit продолжает удерживать слот до передачи и
освобождения мутатором; коллектор не начинает сам освобождать объекты.

Результат присоединяется к уже публикуемому полезному batch. Если такого
batch нет, накопленные смерти публикуются по порогу или предельному сроку
ожидания, чтобы редкие смерти тоже освобождались. Один проход D обрабатывает
накопленную порцию; отдельный проход на каждую найденную смерть не является
предпочтительной политикой. Порог и срок измеряются вместе с удержанными
байтами. Даже ранее подтверждённую смерть мутатор освобождает по своему
точному повторному чтению, сохраняя существующий контракт.

**Альтернатива.** Проверять смерти только среди выбранных корней C и при
pressure/exit. Это проще и не требует второго курсора, но не обеспечивает
раннего возврата свежих припаркованных смертей; соответствующие обещания
нужно убрать. Переход к этой политике — выбор задержки и памяти, а не
эквивалентная оптимизация полного прохода.

**Проверки будущей реализации.** Цепочка из многих блоков; recall в начале,
середине и у границы блока; смерти только в хвосте; P без свободных мест;
удаление блока курсора собственной сборкой; смена эпохи; unwind после
каждого перемещения. Проверяются граница дополнительных позиций после
recall, последующее достижение хвоста и ровно одна запись на кандидата.

## F4. Порог публикации смертей не является механизмом запуска

**Основание.** В
[«Coming back», строки 38–43](https://github.com/limelight-lang/model/blob/5020d2a095e4435e09e27b0c75e8787917da6248/dev/design/the-collector-keeps-the-live-roots.md#L38-L43)
C вызывает обслуживание после истечения stamp. Смерти обнаруживаются
внутри grant. В
[описании задержки, строки 133–146](https://github.com/limelight-lang/model/blob/5020d2a095e4435e09e27b0c75e8787917da6248/dev/design/the-collector-keeps-the-live-roots.md#L133-L146)
порог 32 назван самостоятельным условием, а ухудшение метрик лечится
снижением порога до 1.

Пусть R пуст, C свежая, P пуста, 32 припаркованных объекта завершили
смерть. Нет причины дать grant до истечения C. Существующий
[`retire_at_the_poll`](https://github.com/limelight-lang/model/blob/5020d2a095e4435e09e27b0c75e8787917da6248/src/cycle/queue.rs#L1338-L1374)
ниже порога R выполняет собственный проход; C этому проходу недоступна.
Само уменьшение 32 до 1 grant не создаёт.

Из трёх вариантов выбранному правилу соответствует A:

| Вариант | Запуск | Цена и предел обещания |
|---|---|---|
| A. Срок проверки | Непустая C получает ограниченное обслуживание по сроку, независимо от её epoch stamp | Нет нового действия на каждом free, но полностью живая C тоже вызывает grant и удержание освобождений |
| B. Сигнал существующего счётчика | Уже вооружённый проход retirement замечает непустую C и публикует запрос обслуживания, даже при пустом R | Редкий дополнительный доступ на poll; счётчик всех смертей не становится точным счётчиком смертей C |
| C. Ожидание эпохи | Проверка только при другом полезном grant или истечении C | Наименьшее новое состояние; ранний возврат по порогу 32 больше не обещается |

**Предпочтительное исправление — A вместе с F3.** Коллектор сам хранит
срок и место проверки C; в free-path нет новых чтений или атомарных
операций, в poll нет нового поиска C и публикации запроса о её смертях.
Согласие на grant использует существующий протокол. Найденные смерти
передаются порциями по правилу F3, а grant без полезных постов заканчивается
в `FREE`, без обработки P мутатором.

Нужно назвать срок и хранение прогресса; срок делает запись готовой
к обслуживанию, но сам по себе не гарантирует wall-time возврата памяти.
Затем нужны согласие мутатора, продвижение по C, место в P и открытый poll
для формы D. Нельзя называть 8 секунд сроком физического освобождения.

**B не рекомендован:** он добавляет мутатору обслуживание нового
состояния. Кроме того, в B нельзя незаметно считать порог точным: существующий retirement
обнуляет общий счётчик в некоторых ветках и адаптирует `retire_after`.
Нужно отдельно определить, что оставляет запрос незавершённым, как он
подтверждается коллектором и что происходит с остатком C. Возвращаться к B
имеет смысл только если замер покажет, что его редкий сигнал уменьшает
суммарную работу или задержку самого мутатора относительно A. Простота
коллектора для этого недостаточна. C можно оставить как контроль опыта
с более долгим удержанием памяти.

**Проверки будущей реализации.** R и P пусты, stamp C свежий; ровно 1,
31, 32 и 33 завершённых смерти; новых регистраций нет, поток продолжает
poll. Отдельно `cap 0`, временный закрытый gate, частые recalls и отказ
памяти. Измерять время до последнего возврата и непустой остаток после
остановки нагрузки, а не только среднее удержание во время её работы.

## F6. Выигрыш цепочки нужно отделить от выигрыша формы D

**Основание.** Предложение объединяет отказ от открытия трассировки,
перенос хранения корней и отсутствие stamping для batch без постов.
Сравнение всего пакета с текущим кодом не отвечает, какая часть нужна.
Отдельный опыт записи byte 6 из раздела «What waits for a measurement»
этого сравнения не заменяет.

**Предпочтительный опыт.** Одинаковые heaps, параметры и размещение потоков:

| Вариант | Обработка P без `Proposed` | Хранение корней и live list |
|---|---|---|
| A. Актуальная база | Существующий путь | Существующая deferred lane и stamping |
| B. Только форма D | Проход без trace window | Та же deferred lane, тот же порядок повторных попыток и stamping |
| C. Форма D и цепочка | Проход без trace window | C с исправлениями F1–F4; список batch без постов возвращает коллектор |

B специально сохраняет disposition `ReadLive` в прежнюю deferred lane.
Если одновременно возвращать их прямо в R, это уже дополнительная
политика повторного обхода, и чистое сравнение A/B потеряно. Для B требуется
обработка live list, владение токеном и гарантия пустого P перед `FREE`.
У ранга формы D необходимо сохранить более сильное arming и не потерять
retirement, который её проход не выполнил: проверить существующее
`arm_to_retire_if_the_count_stands`, а не только сброс через
`spend_an_arming_for_the_verdicts`.

Читать разности B−A и C−B. B — контроль вклада формы D, а не причина
оставлять обычные `ReadLive` и `Unwalked` на мутаторе. Целевой результат C:
меньше действий мутатора за счёт собственной работы коллектора, с проверкой
ожидания токена и удержанной памяти. Дополнительные инструкции коллектора
сами по себе не отвергают C.

**Stamping.** Для batch без постов целевой путь не передаёт мутатору live
list и не вооружает проход ради stamping. Для batch с постами перенос
записи byte 6 коллектору тоже соответствует правилу, но требует отдельного
доказательства совместимости с широкими записями заголовков. После него
сравниваются stamping коллектором и отсутствие stamping с повторной
работой коллектора; существующий stamping мутатором остаётся контрольной
базой. Простое удаление stamping ещё не означает меньше работы мутатора:
оно может увеличить его последующую трассировку предложений. Решает
полная работа мутатора на одинаковой полезной нагрузке, включая эти трассы.

Нагрузки должны включать полностью живую C без новых регистраций, смесь
живых корней и мусора, C больше `64 × K`, повторные recalls, смерть после
парковки, отказ выделения блока и остановку нагрузки с дальнейшими poll.
Размещения — свободное ядро для коллектора и конкуренция за ядра;
отдельный режим `cap 0` проверяет собственную обработку мутатора.

Метрики:

- инструкции, cycles и полезная работа мутатора; задержки poll и возврата
  токена, включая хвост распределения;
- время и прочитанные позиции коллектора, попытки из R/C, возраст старейшей
  записи, число повторных обходов живого ядра;
- пиковые и интегральные удержанные байты, GC blocks и отказы, время до
  последнего освобождения после остановки нагрузки и оставшийся мусор.

Порог «не более 10 %» из исходного предложения можно сохранить как один
критерий сравнения памяти, но он не доказывает отсутствие голодания и не
заменяет проверку остатка. Снижение порога смертей допускается оценивать
только после появления действующего механизма запуска из F4.
